## 1. Global tile: which corner is (originX, originY), and how do image axes map to the mission frame?

**Where:** docs/06 §6 ("Global tile ... draw at `originX, originY` with `resMPx`") and the
docs/02 `global_tile` table.

**Why it matters:** the mapper's `/fuse` (P3) writes `originX, originY` and the pixels, and MapView
(P3) draws them. If the writer and the drawer assume different corners or axes, the fused map
lands shifted or mirrored in replay (I3 gate). Local tiles are already pinned down: docs/00 §4
says image-up = rover +x, image-left = rover +y. Global tiles have no equivalent sentence.

**Context:** a global tile is one 512 px square cut from the fused, mission-frame mosaic. It is
axis-aligned, not rotated by heading like a local tile. `ix, iy` are its grid column/row and
`tileId = g_<run>_<ix>_<iy>`.

| Option | Image orientation | (originX, originY) is | Notes |
|---|---|---|---|
| **A (recommended)** | image-up = mission +x, image-left = mission +y (same as local tiles and MapView's screen axes) | the tile's **minimum-x, minimum-y corner** (= image bottom-right corner), in metres | Extent: x ∈ [originX, originX + hPx·resMPx], y ∈ [originY, originY + wPx·resMPx]. `ix` counts along +x, `iy` along +y. MapView draws with no extra rotation. **fake_mapper does this today.** |
| B | same as A | the mission coordinates of the **image's top-left corner** (= maximum-x, maximum-y) | Matches image-array indexing (row 0, col 0) but the extent runs toward negative x and y, which is easy to get wrong. |
| C | conventional "map" layout: image-right = mission +x, image-up = mission +y | the minimum-x, minimum-y corner (= image bottom-left) | Familiar GIS convention, but it's rotated 90° from local tiles and MapView, so every global tile would need an extra rotation when drawn. |

Also part of this item: (originX, originY) refers to the **pixel corner, not the pixel center**
(recommended for all options).

**Decision (P4):** ☐ A ☒ B ☐ C ☐ other: ____________
**Doc to update:** docs/06 §6 (add one sentence like docs/00 §4 has for BEV tiles).

> **Resolved 2026-10-24:** P4 picked **B** in docs/06 §6 (`main` 5fd9a27): origin = mission xy of
> the tile's top-left pixel corner (max x, max y), image up = +x, image left = +y,
> `x = originX − row·resMPx`, `y = originY − col·resMPx`. fake_brain slices with `ix` = column and
> `iy` = row. P3 updated `mocks/fake_mapper.py` to match (branch `p3/mocks-bradford`).

## 4. Small: one brain test fails on Windows (encoding)

**Where:** `gx10/brain/tests/test_settings_match_doc00.py`, line 12: `DOC00.read_text()`.

**What happens:** on Windows, `read_text()` without an encoding uses cp1252, and doc 00 contains
UTF-8 characters, so the test fails with `UnicodeDecodeError`. It passes on Linux/macOS and with
`PYTHONUTF8=1`. Anyone running `make test` on a Windows laptop hits it.

**Suggested fix (your file):** `DOC00.read_text(encoding="utf-8")`. The same applies to
`marsrover_shared/eventlog.py` `read()` if events ever contain non-ASCII text.
**Decision (P4):** ☒ fix. Every text read in P4 code now passes `encoding="utf-8"` (the test, settings.py, app.py, vision_client.py, eventlog.py, fake_brain.py). Verified with `python -X warn_default_encoding`: no warnings left in P4 code. **P3, one for you:** `gx10/mapper/tests/test_store.py:45` reads text without an encoding (same Windows failure).
